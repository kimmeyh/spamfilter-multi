# Sprint 54 F141 -- Android / Google Play Re-Expansion Deep Dive (findings)

**Date**: 2026-08-03. **Scope**: current-state re-verification of every GP-*/F94/F95 HOLD item (last reviewed Sprint 39, 2026-05-25 -- over two months and Sprints 40-53 of Windows-focused work stale), a per-screen UI-adaptation assessment (all 23 screens under `mobile-app/lib/ui/screens/`), and non-UI/backend changes needed for Android to work correctly. Analysis/planning only -- **no app code was changed by this task**.

**Outcome**: the Android/Google Play track is in a materially different state than the Sprint 39-era backlog text implies. Several items are genuinely stale (a decision the backlog still frames as open was already made in an Accepted ADR and never executed; a "4-8h SDK update" task turns out to already be satisfied by the current toolchain). More importantly, this deep dive surfaced **two architecture-level findings not previously documented anywhere**: the Android bottom-navigation shell has two non-functional placeholder tabs, and the desktop app's *default* screen (`no_rule_review_screen.dart`, established by F135) has **zero navigation entry point on Android at all**. Sprint 43's prior architecture deep dive (`SPRINT_43_F103_ARCHITECTURE_DEEP_DIVE.md`) rated Android's platform-architecture status "OK (deferral is documented)" -- that was accurate for what existed at Sprint 43, but the gap between Windows and Android has widened substantially since, through Sprints 51-52's navigation/account-selection overhaul, which was built for desktop only.

**Governing direction established during this deep dive (Harold, 2026-08-03)**: *"All the UIs (now with the Windows UI being the default) should use the same UI and tools unless they cannot -- then they should adapt as needed for the needs of the platform"* (UI), and *"same architectural principle for all the non-UI components -- reuse whatever possible, exactly as is, but adjust where necessary"* (backend/services). **Clarified same day**: the app was built Android-first for early MVP speed, then switched to the Windows Store App style UI and architecture once that became the priority -- so **Windows' current architecture and tooling is the baseline that takes precedence, not "whichever platform already has code."** It is explicitly OK to remove existing Android UI/backend code and replace it with Windows' pattern, adjusting only where Android has a genuine platform constraint. Harold confirmed directly (2026-08-03) this applies to all three of Findings 1/2/3 below (the bottom-nav shell, the No-Rule screen gap, and the old background-scan scaffolding) -- remove and replace all three, not a narrower subset. This resolves both architecture-level findings' "which direction" question -- Section 4 records the answer, not an open question -- and should govern EVERY future Android-track sprint's scoping, not just this deep dive's findings. Confirmed: F142/F143/F144 (recorded in `ALL_SPRINTS_MASTER_PLAN.md`) stay HOLD for a future dedicated Android sprint -- no code changes are part of Sprint 54.

## 2. Per-Screen UI Adaptation Assessment (23 screens)

**Accessibility baseline** (must not regress): Sprint 52's F133 remediation closed 9/9 items across the prod inventory, but coverage today is uneven -- 13 of 23 screens have ZERO `Semantics(` wrapping. Any adaptation work must extend the established wrapper pattern (`ACCESSIBILITY_STANDARDS.md` §2) to touched screens, not just avoid regressing the 10 that already have it.

| Bucket | Screens |
|--------|---------|
| **works-as-is** (16) | account_selection, manual_rule_create, platform_selection, rule_edit, rule_quick_add, rule_test, gmail_oauth, gmail_webview_oauth, gmail_manual_token, help, scan_progress, folder_selection, email_detail_view, safe_sender_quick_add, scan_history, main_navigation (Android path itself is fine; see architecture finding on its content) |
| **needs-adaptation** (5) | account_setup (one unpadded small link), results_display (fixed 3-column grid + touch-target gaps), rules_management (36dp icons + hover-only info reveal + keyboard-modifier multi-select), safe_senders_management (same pattern as rules_management), settings (4-tab crowding risk + Windows-only background-scan branches) |
| **needs-new-pattern** (2) | yaml_import_export (desktop-filesystem-assuming FilePicker calls -- a data-layer change, not a resize), no_rule_review (Ctrl/Shift-click range-select + right-click context menu, zero touch equivalent, AND zero Android entry point today) |

**Concrete, evidence-cited findings** (full detail with file:line references in the sprint transcript; summarized here):

- **results_display_screen.dart** (3246 lines, the largest and highest-traffic screen): a deliberate Sprint 50 fixed 3-column action grid gets tight at 360dp width; a stat/folder chip wrapped in a bare `GestureDetector` and a clear-filter `IconButton` with `constraints: const BoxConstraints()` both fall under the 48dp minimum touch target.
- **rules_management_screen.dart** + **safe_senders_management_screen.dart**: share `list_selection_controller.dart`, which reads `HardwareKeyboard.instance.logicalKeysPressed` for Ctrl/Shift-click multi-select -- no touch equivalent exists. The per-row info `IconButton` is BOTH under 48dp AND hover-gated (`MouseRegion`/`AnimatedOpacity`) -- on touch it is not just small, it is invisible, since there is no hover state.
- **settings_screen.dart**: the 4-tab TabBar could crowd at accessibility font sizes; more importantly several `if (Platform.isWindows)` branches show a "Windows-only" SnackBar for background-scan scheduling on other platforms -- a functional gap, not a layout one (see Section 3).
- **yaml_import_export_screen.dart**: `FilePicker.platform.saveFile(...)` / `pickFiles().path` dereferencing assumes ordinary desktop filesystem access; Android's Storage Access Framework / scoped storage does not guarantee this call pattern works as-is and needs verification against the current `file_picker` plugin version.
- **no_rule_review_screen.dart**: `_handleItemTap` directly reads `isControlPressed`/`isShiftPressed`; `onSecondaryTapDown` opens a right-click context menu. A touch-compatible bulk-action menu (`PopupMenuButton`) already exists and works fine by tap -- it is specifically the multi-item *selection* mechanism that has no touch equivalent.

## 3. Non-UI / Backend Changes Needed

- **Background scanning: old Android-first scaffolding, superseded by Windows' current architecture -- per Harold's clarified direction (2026-08-03), evaluate for REMOVAL and REPLACEMENT following the Windows pattern, not a reconnect.** `BackgroundScanManager`/`BackgroundScanService` (a `workmanager`-based scheduler) exist in source with Android-appropriate config already written (`AndroidNotificationDetails` in `background_scan_notification_service.dart`), but **nothing in the app calls `BackgroundScanService` from anywhere** -- grep across all of `lib/` found zero call sites outside the file itself. This path predates Windows' `WindowsTaskSchedulerService` (per-account scheduling, ADR-0039/0040, F98), which is now the actively-maintained, current-architecture background-scan design. Since Windows takes precedence as the baseline, the right move is an Android implementation that mirrors the CURRENT Windows design (per-account scheduling model, settings/UI wiring, notification approach) as closely as Android allows, substituting `workmanager`/`AlarmManager` only where WorkManager genuinely is Android's equivalent of Windows Task Scheduler (a real platform constraint) -- not preserving the old `BackgroundScanManager` code's own, now-superseded design decisions. Harold confirmed directly this is the intended scope, not a narrower "reconnect as-is."
- **Android 13+ notification permission is entirely unhandled.** No `POST_NOTIFICATIONS` runtime permission request exists anywhere in `lib/` (confirmed by grep). The permission IS auto-merged into the manifest by `flutter_local_notifications`/`workmanager_android` (per Section 1's GP-3 finding), but Android 13+ (API 33+) requires an explicit RUNTIME request in addition to the manifest declaration -- without it, notifications would silently never show, with no error surfaced to the user. Concrete, scoped fix as part of whatever background-scan implementation replaces the old scaffolding.
- **Credential storage and app-data paths are already correctly cross-platform.** `AppPaths` uses `path_provider`'s `getApplicationSupportDirectory()` with no platform special-casing needed; `SecureCredentialsStore` already configures `AndroidOptions()` explicitly (post-F108 `encryptedSharedPreferences` deprecation). No work needed here.

## 4. Architecture-Level Findings and Direction (Harold, 2026-08-03)

Per the Decision-Class Checkpoint Protocol these are findings, not yet-implemented code -- but the governing DIRECTION was clarified by Harold during this deep dive and is recorded here as durable guidance, superseding this document's earlier framing of Findings 1-2 as open either/or questions:

> **"From the architectural documents -- all the UIs (now with the Windows UI being the default) should use the same UI and tools unless they cannot -- then they should adapt as needed for the needs of the platform from a UI and tooling perspective."**

This means: the default posture for EVERY future Android UI/navigation decision is to adopt what desktop already does, and diverge from it only where Android genuinely cannot support the same approach (a real platform constraint -- no keyboard modifiers, no hover, no right-click -- not a preference for "a more native-feeling" alternative). Both findings below are re-framed against that standard rather than left as open design questions.

**Finding 1 -- the Android bottom-nav shell's "Rules" and "Settings" tabs are non-functional placeholders, and the bottom-nav shell itself is a pre-Sprint-51 pattern that predates and diverges from the now-default desktop navigation model.** `main_navigation_screen.dart`'s `_screens` list backs 2 of 3 `NavigationBar` destinations with a literal `_PlaceholderScreen` reading "Manage rules from the Account Details screen" / "Configure account settings from Account Details screen." Both real screens (`RulesManagementScreen`, `SettingsScreen`) require an `accountId` the bottom-nav shell has no mechanism to supply -- there is no persistent "selected account" context at the Android nav-shell level today, unlike desktop's `SelectedAccountProvider`. **Per the stated direction, the default assumption for a future implementation sprint is: Android should adopt the SAME `SelectedAccountProvider` session-scoped account model and `StandardAppBarActions` icon-based navigation desktop now uses, replacing the bottom-nav shell, rather than inventing a separate Android-native information architecture.** A bottom nav bar is not something Android *cannot* do without -- AppBar-icon navigation works identically on touch -- so this is exactly the "unless they cannot" exception NOT applying; the shared model should be adopted here.

**Finding 2 -- `no_rule_review_screen.dart`, the desktop app's DEFAULT screen (F135), has zero Android entry point.** `StandardAppBarActions.build` gates the "Review No Rule Items" AppBar icon to `Platform.isWindows` across all 15 screens sharing that builder; `MainNavigationScreen`'s Android branch never reaches `_DesktopDefaultScreen` (which is what shows `NoRuleReviewScreen`). This means Sprint 46's F39 cross-account review screen -- arguably the app's core workflow, since it is what desktop users see by default -- is entirely unreachable on Android. **Per the stated direction: Android's default screen should be the SAME `NoRuleReviewScreen` desktop uses (once Finding 1's shared navigation model lands), reached the same way.** The one place a genuine platform-driven adaptation is warranted is the screen's SELECTION mechanism specifically: Ctrl/Shift-click and right-click have no touch equivalent (a real "cannot" case, not a preference), so the touch-adapted redesign (long-press-to-select + contextual action bar) is the correct kind of platform-specific tooling adaptation the stated direction anticipates -- everything else about the screen (its content, its role as the default, its bulk-action menu which already works fine by tap) should stay the same as desktop.

**Finding 3 (weaker signal, backend-adjacent, flagged for completeness)** -- Settings screen's Background tab cannot show anything meaningful for Android until Finding 1's shared-navigation-model work lands (which unblocks replacing the old background-scan scaffolding per Section 3); this is a sequencing note, not an open decision -- the direction above already answers what the eventual Background tab should look like (the same as desktop's, per Windows' architecture).

**Not architecture-class**: the `ListSelectionController` touch redesign needed by `rules_management_screen.dart`/`safe_senders_management_screen.dart` is real interaction-design work but stays confined to those screens' row widgets -- it introduces no new screens or app-level navigation, so it does not itself require a sign-off gate, though its scope is large enough that Harold may want visibility before it is scheduled.
